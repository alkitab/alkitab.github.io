УЧЕБНИК ПО ЦИКЛУ РАЗРАБОТКИ
===========================

От идеи до сопровождения — соло
===============================

Этот учебник объединяет знания из шести предыдущих: HTML, CSS, SVG,
PHP, SQLite+PHP, Хостинг. Мы рассмотрим полный жизненный цикл
веб-сайта глазами одного человека — соло-веб-мастера, который делает
всё сам: от сбора требований до обновления и развития.

Аудитория — самостоятельный мастер, уже владеющий основами HTML, CSS,
PHP, SQLite и настройки сервера. Учебник не учит технологиям с нуля, а
показывает, как их соединить в рабочий процесс. Все этапы — анализ,
дизайн, вёрстка, программирование, деплой, запуск, сопровождение,
развитие — рассмотрены последовательно, с чек-листами и задачами.

ГЛАВА 1. ВВЕДЕНИЕ В ЖИЗНЕННЫЙ ЦИКЛ САЙТА
========================================


1.1. Что такое жизненный цикл
-----------------------------
Жизненный цикл сайта — это последовательность этапов от возникновения
идеи до прекращения поддержки. Сайт не делается один раз и навсегда:
он рождается, развивается, иногда умирает. Понимание цикла позволяет
планировать работу и не теряться между задачами.

Классические этапы:

• Анализ — что и зачем делаем
• Дизайн — как это выглядит
• Вёрстка — HTML/CSS/SVG по макету
• Программирование — PHP, БД, логика
• Деплой — перенос на боевой сервер
• Запуск — SEO, метрики, анонс
• Сопровождение — контент, бэкапы, мониторинг
• Развитие — новые фичи, рефакторинг
• Завершение — архив, перенос, закрытие


1.2. Особенности соло-разработки
--------------------------------
Соло-веб-мастер — это T-образный специалист: глубокий в одной области
(например, вёрстка) и широкий в остальных (сервер, БД, дизайн,
копирайтинг, маркетинг). Вы не станете экспертом во всём, но должны
понимать достаточно, чтобы сделать работающий сайт от начала до конца.

Главные плюсы соло:

• Полный контроль над решениями
• Никаких совещаний и согласований
• Скорость — от идеи до деплоя за вечер
• Дешевизна — не нужно платить команде

Главные минусы:

• Один источник ошибок — некому проверить
• Узкое горлышко — вы сами, нельзя распараллелить
• Выгорание — трудно переключаться между ролями
• Сложные технологии без команды — предел роста


1.3. Связка с предыдущими учебниками
------------------------------------
Этот учебник — кульминация серии. Он не повторяет детально то, что
разобрано раньше, а показывает, как соединить шесть дисциплин в один
рабочий процесс:

• HTML — структура страниц (глава 5)
• CSS — стили и адаптив (глава 5)
• SVG — иконки и графика (глава 5)
• PHP — бэкенд-логика (глава 6)
• SQLite+PHP — база данных (глава 6)
• Хостинг — деплой и сопровождение (главы 7, 9, 11)


1.4. Типовые ошибки соло-мастера
--------------------------------
Опыт собирает шишки. Самые частые ошибки новичков:

• Всё и сразу — пытаться сделать "как у больших"
• Без ТЗ — начать кодить без понимания целей
• Без бэкапов — терять данные при первом сбое
• Без документации — через полгода не вспомнить, что где
• Без Git — ручные бэкапы папок, путаница версий
• Пропустить дизайн — сразу в код, переделывать 5 раз
• Игнорировать безопасность — пока не взломают


1.5. Маленький сайт — что это
-----------------------------
В этом учебнике ориентир — малый сайт: лендинг, визитка, корпоративный
сайт до 20 страниц. Примеры: сайт-портфолио фотографа, сайт небольшой
кофейни, визитка частного юриста, лендинг онлайн-курса.

Малый сайт отличается:

• Бюджет: 5–50 тыс. рублей или бесплатно для себя
• Срок: 1–4 недели от идеи до запуска
• Команда: 1 человек
• Технологии: HTML + CSS + PHP + SQLite
• Хостинг: shared или самый дешёвый VPS ($5/мес)
• Контент: 5–20 страниц, обновляется редко

Для среднего и крупного сайта цикл тот же, но каждый этап длиннее и
сложнее. Принципы остаются.

ГЛАВА 2. ОКРУЖЕНИЕ РАЗРАБОТЧИКА
===============================


2.1. Что нужно для старта
-------------------------
Прежде чем писать первую строку кода, настройте рабочее место.
Минимальный набор соло-мастера:

• Редактор кода (VS Code — бесплатный стандарт)
• Терминал (встроенный в macOS/Linux, Windows Terminal)
• Git (для версионирования)
• PHP локально (для запуска dev-сервера)
• SQLite3 CLI (для работы с БД)
• Браузер с DevTools (Chrome или Firefox)
• SSH-клиент (встроен в ОС)


2.2. VS Code и расширения
-------------------------
VS Code — самый популярный бесплатный редактор. Из коробки подходит
для HTML/CSS, но для PHP нужны расширения:

• PHP Intelephense — автодополнение и подсказки
• PHP DocBlocker — генерация комментариев
• PHP Intellisense — навигация по коду
• Live Server — автообновление HTML в браузере
• GitLens — подсказки по Git прямо в коде
• Prettier — автоформатирование
• SQLite Viewer — просмотр .sqlite файлов

Установка через CLI:

code --install-extension bmewburn.vscode-intelephense-client
code --install-extension ritwickdey.liveserver
code --install-extension eamodio.gitlens
code --install-extension esbenp.prettier-vscode
code --install-extension qwtel.sqlite-viewer


2.3. Локальный сервер PHP
-------------------------
PHP имеет встроенный веб-сервер для разработки. Запустите его в папке
проекта:

cd ~/projects/mysite
php -S localhost:8000

# Теперь сайт доступен:
# http://localhost:8000

Это всё, что нужно для разработки. Никакого Apache, Nginx, Docker,
Composer для малого сайта. Откройте URL в браузере — и работает.


2.4. Структура папок проекта
----------------------------
Создайте логичную структуру сразу. Типичная для соло-проекта:

mysite/
    public/           # корень сайта
        index.php     # точка входа
        .htaccess     # настройки Apache
        assets/
            css/
            js/
            img/
    app/              # PHP-код (не доступен через веб)
        Database.php
        Models/
        Controllers/
    data/             # НЕ доступен через веб
        database.sqlite
    config/
        db.php
    migrations/
        001_create_users.sql
    README.md
    CHANGELOG.md
    .env               # секреты, в .gitignore!
    .env.example       # шаблон, в Git
    .gitignore

Главный принцип: всё, что доступно через веб, — в public/. PHP-код,
БД, конфиги — вне public. Это безопасность по умолчанию.


2.5. .env и секреты
-------------------
Файл .env хранит секреты: пароли, ключи API. Никогда не коммитьте его
в Git. Создайте .env.example как шаблон с пустыми значениями:

# .env.example
DB_PATH=./data/database.sqlite
SMTP_HOST=
SMTP_USER=
SMTP_PASS=
DEBUG=true

# При установке проекта:
# cp .env.example .env
# nano .env  # заполнить значения


2.6. SSH-ключи и доступ к серверу
---------------------------------
Если у вас уже есть VPS, настройте SSH-ключи и конфиг. Безопасность и
удобство — два плюса сразу:

# Создать ключ (один раз)
ssh-keygen -t ed25519 -C "my@machine"

# Скопировать на сервер
ssh-copy-id user@your-server.com

# ~/.ssh/config для удобства
Host mysite
    HostName your-server.com
    User deploy
    IdentityFile ~/.ssh/id_ed25519
    ServerAliveInterval 60

# Теперь: ssh mysite

ГЛАВА 3. GIT-WORKFLOW ДЛЯ СОЛО-ПРОЕКТА
======================================


3.1. Зачем Git одному
---------------------
Git — это не только для команд. Даже соло-разработчик получает от него
пользу:

• История изменений — что и когда меняли
• Откаты — вернуться к рабочей версии
• Ветки — пробовать фичи, не ломая main
• Бэкап кода на GitHub/GitLab
• Деплой через git pull на сервер
• Issue-трекер для своих же задач


3.2. Инициализация и .gitignore
-------------------------------
Создаём репозиторий в папке проекта:

cd ~/projects/mysite
git init
git branch -m main  # современный стандарт

# Создаём .gitignore
cat > .gitignore <<EOF
# Секреты
.env

# База данных
data/*.sqlite
data/*.sqlite-journal

# Зависимости (если будут)
vendor/
node_modules/

# Логи и временные файлы
*.log
.DS_Store
Thumbs.db
EOF


3.3. Базовый workflow
---------------------
Простой цикл — для соло-проекта достаточно:

# Изменения → индекс → коммит
git add .
git commit -m "feat: добавлена форма обратной связи"

# Запушить на GitHub
git push origin main


3.4. Ветки для фич
------------------
Хотя вы один, ветки помогают изолировать эксперименты. Если фича
затянется или не получится — просто удалите ветку, main останется
рабочим.

# Создать ветку для фичи
git checkout -b feature/contact-form

# ... работаем ...
git add .
git commit -m "feat: форма обратной связи"

# Готово — вливаем в main
git checkout main
git merge feature/contact-form
git branch -d feature/contact-form  # удалить ветку


3.5. Конвенция коммитов
-----------------------
Conventional Commits — стандарт формата сообщений. Помогает понять
историю и автоматически генерировать changelog:

• feat: новая функциональность
• fix: исправление бага
• docs: документация
• style: форматирование, без логики
• refactor: переработка без изменения поведения
• test: добавление тестов
• chore: обслуживание проекта, зависимости
• perf: улучшение производительности

git commit -m "feat: добавлена корзина"
git commit -m "fix: исправлен расчёт скидки"
git commit -m "docs: обновлён README"
git commit -m "refactor: вынес БД в класс Database"


3.6. Теги версий
----------------
Когда сайт достигает очередной стабильной версии, пометьте это тегом.
Semantic Versioning: MAJOR.MINOR.PATCH.

git tag -a v1.0.0 -m "Первый релиз"
git push origin v1.0.0

# MAJOR — несовместимые изменения
# MINOR — новые фичи, обратная совместимость
# PATCH — исправления багов


3.7. Откаты
-----------
Если что-то сломалось:

# Отменить последний коммит,
# изменения останутся в файлах
git reset --soft HEAD~1

# Отменить и стереть изменения
git reset --hard HEAD~1

# Безопаснее — создать revert-коммит
git revert HEAD

# Посмотреть историю
git log --oneline
git log -p path/to/file.php  # с изменениями

ГЛАВА 4. АНАЛИЗ И ПРОЕКТИРОВАНИЕ
================================


4.1. Метод 5W
-------------
Прежде чем писать код, ответьте на 5 вопросов:

• Who — кто целевая аудитория?
• What — что они должны делать на сайте?
• Where — где они приходят (поиск, соцсети, реклама)?
• When — когда (срок запуска)?
• Why — зачем вам этот сайт?

Пример: сайт-визитка фотографа. Who — невесты 25–35 лет. What —
посмотреть портфолио, узнать цены, оставить заявку. Where — Instagram,
поиск Яндекса. When — к сезону свадеб (март). Why — получать заказы,
не объяснять по телефону.


4.2. Цели сайта
---------------
У сайта должна быть измеримая цель. Не «чтобы был», а конкретно:

• Получать 5 заявок в неделю через форму
• Подписать 100 человек на рассылку за месяц
• Продавать 3 курса в месяц
• Привлечь 1000 уникальных посетителей в месяц

Цель определяет структуру сайта. Если цель — заявки, форма должна быть
заметной на каждой странице. Если продажи — кнопка «купить» превыше
всего.


4.3. Карта сайта
----------------
Список всех страниц с иерархией. Для малого сайта это обычно:

Главная
    Услуги
        Услуга 1
        Услуга 2
    Портфолио
    О компании
    Блог
        Пост 1
        Пост 2
    Контакты

Карта помогает оценить объём работы и спланировать вёрстку. Если
страниц больше 20 — это уже не малый сайт, нужна более сложная
архитектура.


4.4. Прототип
-------------
Прототип — это чёрно-белая раскладка блоков без дизайна. Можно
рисовать в Figma, Penpot, или даже на бумаге. Цель — согласовать
структуру до того, как вы потратите время на дизайн.

• Где заголовок, где меню, где основной контент
• Какие элементы на каждой странице
• Куда идут ссылки из меню
• Где формы и кнопки

Для соло-мастера прототип — это разговор с самим собой. Нарисовали,
посмотрели — что-то не так, переделали за 5 минут. В коде такая
переделка заняла бы день.


4.5. Дизайн-макет
-----------------
Когда прототип устраивает, переходим к макету — цветному, с
типографикой, фотографиями, иконками. Инструменты:

• Figma — бесплатная,行业标准
• Penpot — open-source аналог Figma
• Photoshop/GIMP — для тех, кто привык
• На бумаге — для быстрых набросков

Для малого сайта достаточно макета 3–4 ключевых страниц: главная,
внутренняя (услуги/блог), контакты. Остальные страницы строятся по
тому же шаблону.


4.6. Дизайн-система
-------------------
Соберите все цвета, шрифты, отступы в один документ. Это сэкономит
время на вёрстке:

Цвета:
  primary:    #0066cc (синий)
  secondary:  #ff6600 (оранжевый)
  bg:         #ffffff
  text:       #1a1a1a
  muted:      #666666

Шрифты:
  headings: "Montserrat", sans-serif
  body:    "Open Sans", sans-serif

Отступы (8px система):
  xs: 4px   s: 8px   m: 16px
  l: 24px   xl: 32px 2xl: 64px

Размеры шрифтов:
  body: 16px
  h1: 32px   h2: 24px   h3: 20px
  small: 14px

ГЛАВА 5. ВЁРСТКА И ДИЗАЙН
=========================


5.1. План вёрстки
-----------------
Когда макеты готовы, переносим их в код. Порядок работ:

• HTML-структура всех страниц
• CSS-стили — общие + компоненты
• Адаптив — mobile-first
• SVG-иконки и графика
• Шрифты через Google Fonts или self-hosted
• Метаданные: title, description, Open Graph


5.2. HTML по стандарту
----------------------
Используйте HTML5 по учебнику HTML: семантические теги, корректную
иерархию заголовков, доступность. Базовый каркас:

<!DOCTYPE html>
<html lang="ru">
<head>
  <meta charset="utf-8">
  <meta name="viewport"
        content="width=device-width,
                 initial-scale=1">
  <title>Мясная лавка «Мясоров»</title>
  <meta name="description"
        content="Свежее мясо с доставкой">
  <link rel="stylesheet"
        href="/assets/css/style.css">
</head>
<body>
  <header>...</header>
  <main>...</main>
  <footer>...</footer>
</body>
</html>


5.3. CSS по стандарту
---------------------
CSS из соответствующего учебника. Mobile-first: сначала мобильные
стили, потом медиазапросы для больших экранов. БЭМ или простые классы
— на ваш выбор.

/* Базовые сбросы */
*, *::before, *::after { box-sizing: border-box; }
body {
  margin: 0;
  font-family: "Open Sans", sans-serif;
  line-height: 1.5;
  color: #1a1a1a;
}

/* Mobile-first */
.container { padding: 0 16px; }

/* Планшет и больше */
@media (min-width: 768px) {
  .container { max-width: 720px;
               margin: 0 auto; }
}

/* Десктоп */
@media (min-width: 1200px) {
  .container { max-width: 1140px; }
}


5.4. SVG-графика
----------------
Иконки и логотип — в SVG по учебнику. Inline SVG для интерактивных
иконок с hover-эффектами, внешний спрайт для набора иконок:

<!-- public/assets/icons.svg -->
<svg xmlns="http://www.w3.org/2000/svg"
     style="display:none">
  <symbol id="i-phone" viewBox="0 0 24 24">
    <path fill="currentColor" d="M6 2 L18 22 ..."/>
  </symbol>
</svg>

<!-- в HTML -->
<a href="tel:+78001234567" class="phone">
  <svg width="16" height="16"><use
    href="/assets/icons.svg#i-phone"/></svg>
  +7 800 123-45-67
</a>


5.5. Чек-лист вёрстки
---------------------
Перед тем как переходить к программированию, проверьте:

• HTML проходит валидацию validator.w3.org
• Все изображения имеют alt
• Адаптив работает на 375px, 768px, 1280px
• Шрифты загружаются с Google Fonts или self-hosted
• Цвета соответствуют дизайн-системе
• Иерархия заголовков: один h1 на странице
• Контакты и формы кликабельны
• Картинки оптимизированы (WebP/AVIF, lazy loading)
• SVG-иконки используют currentColor
• Нет inline-стилей (style=...) — всё в CSS

ГЛАВА 6. ПРОГРАММИРОВАНИЕ (PHP+БД)
==================================


6.1. Когда начинается программирование
--------------------------------------
Если сайт статичный — 5 страниц визитки без форм — PHP не нужен.
Просто HTML+CSS. Но как только появляется:

• Форма обратной связи → нужен PHP
• Блог с добавлением постов → нужен PHP + БД
• Корзина в магазине → нужен PHP + БД + сессии
• Авторизация → нужен PHP + БД + сессии
• Поиск по сайту → нужен PHP + БД


6.2. Точка входа index.php
--------------------------
Современный подход — единая точка входа. Все запросы идут через
index.php, который маршрутизирует:

# public/.htaccess
RewriteEngine On
RewriteCond %{REQUEST_FILENAME} !-f
RewriteCond %{REQUEST_FILENAME} !-d
RewriteRule ^ index.php [QSA,L]

# public/index.php — точка входа
<?php
require_once __DIR__ . '/../config/db.php';

$uri = parse_url($_SERVER['REQUEST_URI'],
                 PHP_URL_PATH);

switch ($uri) {
    case '/':            require 'home.php'; break;
    case '/contacts':    require 'contacts.php'; break;
    case '/feedback':
        if ($_SERVER['REQUEST_METHOD'] === 'POST') {
            // обработка формы
        }
        require 'feedback.php';
        break;
    default:
        http_response_code(404);
        require '404.php';
}


6.3. Форма обратной связи
-------------------------
Самая частая задача — форма обратной связи. Связка HTML + PHP по
учебникам HTML и PHP:

<!-- feedback.php -->
<form method="post">
  <input name="name" required placeholder="Имя">
  <input type="email" name="email"
         required placeholder="Email">
  <textarea name="message" required></textarea>
  <button>Отправить</button>
</form>

<?php
if ($_SERVER['REQUEST_METHOD'] === 'POST') {
    $name = trim($_POST['name']);
    $email = trim($_POST['email']);
    $msg = trim($_POST['message']);

    // Валидация
    if (!filter_var($email, FILTER_VALIDATE_EMAIL)) {
        die('Некорректный email');
    }

    // Сохранение в БД
    db()->prepare(
        'INSERT INTO messages
            (name, email, message, created_at)
         VALUES (?, ?, ?, ?)'
    )->execute([$name, $email, $msg, date('c')]);

    // Email уведомление (опционально)
    mail('owner@example.com',
         'Новое сообщение с сайта',
         "От: $name <$email>\n\n$msg");

    header('Location: /feedback?sent=1');
    exit;
}
?>


6.4. БД через PDO
-----------------
Подключение и CRUD — по учебнику SQLite+PHP. Создаём таблицу
миграцией:

# migrations/001_create_messages.sql
CREATE TABLE messages (
    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    name        TEXT NOT NULL,
    email       TEXT NOT NULL,
    message     TEXT NOT NULL,
    created_at  TEXT NOT NULL
);

# Применение
sqlite3 data/database.sqlite \
    < migrations/001_create_messages.sql

Класс Database как Singleton — из главы 10 учебника по SQLite:

# config/db.php
<?php
function db(): PDO {
    static $pdo = null;
    if ($pdo === null) {
        $pdo = new PDO(
            'sqlite:' . __DIR__
                     . '/../data/database.sqlite'
        );
        $pdo->setAttribute(PDO::ATTR_ERRMODE,
                          PDO::ERRMODE_EXCEPTION);
        $pdo->setAttribute(PDO::ATTR_DEFAULT_FETCH_MODE,
                          PDO::FETCH_ASSOC);
    }
    return $pdo;
}
?>


6.5. Чек-лист программирования
------------------------------

• Все запросы к БД — через prepare/execute
• Все пользовательские данные валидируются
• При выводе в HTML — htmlspecialchars()
• Пароли хранятся через password_hash()
• Сессия стартует session_start() в начале скрипта
• CSRF-токены в формах, меняющих состояние
• Ошибки логируются, не показываются пользователю
• Файлы .env и database.sqlite вне public/

7.7. Права на файлы
-------------------
Установите правильные права, чтобы Apache мог читать файлы, но не мог
менять код (только владелец):

# Владелец — deploy, группа — www-data

# Каталоги 755, файлы 644

# Папка data/ — запись для www-data
chmod -R 775 /var/www/mysite/data
chown -R deploy:www-data /var/www/mysite/data

# .env — только владелец
chmod 600 /var/www/mysite/.env

9.3. Скрипт бэкапа
------------------
Простейший скрипт для автоматического бэкапа. Поместите в
/home/deploy/backup.sh:

#!/bin/bash
# /home/deploy/backup.sh
set -e

DATE=$(date +%Y%m%d-%H%M)
BACKUP_DIR=/home/deploy/backups
SITE_DIR=/var/www/mysite

mkdir -p $BACKUP_DIR

# Бэкап БД
sqlite3 $SITE_DIR/data/database.sqlite \
    ".dump" | gzip > \
    $BACKUP_DIR/db-$DATE.sql.gz

# Бэкап файлов
tar -czf $BACKUP_DIR/files-$DATE.tar.gz \
    --exclude='*.sqlite' \
    --exclude='*.log' \
    -C /var/www mysite

# Удалить бэкапы старше 30 дней
find $BACKUP_DIR -mtime +30 -delete

echo "[$DATE] Бэкап завершён" >> $BACKUP_DIR/log.txt


Запуск по cron каждый день в 3 часа ночи:

# crontab -e
0 3 * * * /home/deploy/backup.sh >> /var/log/backup.log 2>&1


9.4. Правило 3-2-1 для бэкапов
------------------------------
Профессиональное правило хранения бэкапов:

• 3 копии данных
• 2 разных носителя (диск + облако)
• 1 копия вне офиса/сервера

В нашем случае: оригинал на сервере, копия в backups/ на том же
сервере, и третья копия синхронизируется с облачным хранилищем
(Яндекс.Диск, S3):

# Дополнение к backup.sh
# Синхронизация с облаком (нужен rclone)
rclone copy $BACKUP_DIR/ yandex:backups/mysite/ \
    --max-age 24h --quiet

10.3. Признаки «дурно пахнущего» кода

10.4. A/B-тесты
---------------
Не угадывайте — тестируйте. A/B-тест показывает пользователям две
версии и считает, какая лучше. Для малого сайта без инструментов —
вручную:

<?php
# Простая A/B-раздача
$variant = mt_rand(0, 1) === 0 ? 'A' : 'B';
setcookie('ab_test', $variant, time() + 86400 * 30);
?>

<!-- Версия A -->
<?php if ($variant === 'A'): ?>
  <h1>Лучшие услуги в городе</h1>
<?php else: ?>
  <h1>Услуги с гарантией качества</h1>
<?php endif; ?>

<?php
# В форме передаём вариант
# и позже анализируем конверсию
?>

ГЛАВА 11. БЕЗОПАСНОСТЬ И БЭКАПЫ
===============================


11.1. Угрозы для малого сайта
-----------------------------
Малый сайт — не цель целенаправленной атаки, но боты сканируют весь
интернет 24/7. Самые частые угрозы:

• Подбор пароля к SSH/admin через брутфорс
• Эксплуатация устаревших версий PHP/Apache
• SQL-инъекции через формы поиска
• XSS через комментарии и UGC
• Заливка web-shell через загрузку файлов
• DDoS (редко для малого сайта)


11.2. Регулярные обновления
---------------------------
Главное правило безопасности: обновляйте. Большинство взломов —
эксплуатация известных уязвимостей, для которых уже есть патч:

# Ежемесячно
apt update && apt upgrade -y

# Если есть Composer
cd /var/www/mysite
composer update

# Перезапуск после обновления PHP
systemctl restart apache2  # или php8.3-fpm


11.3. fail2ban и фаервол
------------------------
По учебнику Хостинг. fail2ban банит IP-адреса с большим числом
неудачных входов. ufw закрывает все порты, кроме нужных:

# Установка fail2ban
apt install fail2ban
systemctl enable fail2ban

# Фаервол ufw
ufw default deny incoming
ufw default allow outgoing
ufw allow 22/tcp   # SSH
ufw allow 80/tcp   # HTTP
ufw allow 443/tcp  # HTTPS
ufw enable


11.4. Аудит прав
----------------

13.1. Метод Помодоро
--------------------
Техника управления временем: 25 минут работы + 5 минут перерыв. После
4 помодоро — большой перерыв 15-30 минут. Меняете задачи в перерывах,
не в pomodoro.

Преимущества:

• Чёткие рамки — мозг сфокусирован
• Регулярные перерывы — меньше выгорание
• Легко оценить время: "это 2 помодоро"
• Внешняя дисциплина: таймер на телефоне

Инструменты: TomatoTimer (веб), Forest (iOS/Android), Pomotodo. Или
просто терминальный таймер:

# Простой таймер на 25 минут
sleep 1500 && echo 'Pomodoro done!' && \
  notify-send 'Pomodoro' 'Перерыв!'


13.2. Оценка времени по PERT
----------------------------
Чтобы не обещать себе невыполнимого, оценивайте задачи по трём
сценариям:

• O — оптимистичная (всё идёт идеально)
• M — наиболее вероятная
• P — пессимистичная (что-то пойдёт не так)

Формула PERT: (O + 4M + P) / 6. Например, задача «сделать форму
обратной связи»: O=2ч, M=4ч, P=10ч. Оценка: (2 + 16 + 10) / 6 ≈ 4.7
часа.


13.3. Правило 80/20
-------------------
Принцип Парето: 20% усилий дают 80% результата. Для веб-разработки это
значит:

• 20% страниц дают 80% трафика (главная, услуги, контакты)
• 20% функций дают 80% ценности (форма, прайс, портфолио)
• 20% времени уходит на 80% функционала (донесение до запуска)
• 80% времени — на полировку оставшихся 20%

Соло-мастеру важно не впасть в перфекционизм. Запустите "минимально
жизнеспособный сайт" (MVP), получите первых пользователей, потом
дорабатывайте по обратной связи.

13.5. Минимизация выгорания
---------------------------
Соло-разработка — марафон, не спринт. Признаки выгорания:

• Не получается заставить себя открыть редактор
• Лёгкие задачи кажутся неподъёмными
• Появляется раздражение от проекта
• Снижается качество кода, больше багов
• Пропадают идеи и энтузиазм

Профилактика:

• Не работать вечерами и выходными (если не горит)
• Брать 1-2 выходных от проекта в неделю
• Чередовать типы задач: дизайн, код, контент, общение
• Делать физическую разминку каждый час
• Иметь хобби вне веб-разработки
• Общаться с другими: митапы, форумы, чаты

13.8. Задача 3: скрипт бэкапа
-----------------------------
Напишите bash-скрипт для ежедневного бэкапа сайта (файлы + БД) с
удалением старых. Решение:

#!/bin/bash
# /home/deploy/backup.sh
set -e

DATE=$(date +%Y%m%d-%H%M)
BACKUP_DIR=/home/deploy/backups
SITE_DIR=/var/www/mysite
RETENTION_DAYS=30

mkdir -p $BACKUP_DIR

# БД
sqlite3 $SITE_DIR/data/database.sqlite \
    ".dump" | gzip > \
    $BACKUP_DIR/db-$DATE.sql.gz

# Файлы (без БД и логов)
tar -czf $BACKUP_DIR/files-$DATE.tar.gz \
    --exclude='*.sqlite' \
    --exclude='*.sqlite-journal' \
    --exclude='*.log' \
    -C /var/www mysite

# Удаление старых
find $BACKUP_DIR -mtime +$RETENTION_DAYS -delete

# Лог
echo "[$DATE] OK" >> $BACKUP_DIR/backup.log

# Cron: каждый день в 3:00
# 0 3 * * * /home/deploy/backup.sh
